# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project Overview

An application for tracking workouts and diet, built around a **trainer/trainee** relationship: one trainer authors fixed workout and diet plans for each of their trainees, and trainees log their actual sessions/food against those plans. Stage 1 is intentionally minimal: get core logging working end-to-end for a small group of users (~10) before adding scale, polish, or advanced features.

**Do not over-engineer.** Avoid speculative abstractions, premature microservices, multi-tenant complexity, or infrastructure aimed at scale we don't need yet. Favor the simplest Django/React implementation that correctly models the data below. Scalability is a *future* concern — note it in comments/TODOs if relevant, but don't build for it now.

## Tech Stack

- **Backend:** Django (+ Django REST Framework for the API)
- **Frontend:** React (web app)
- **Database:** Postgres preferred if available; SQLite is acceptable for Stage 1 local dev
- **Auth:** Simple session or token auth is sufficient for ~10 users — no need for complex SSO/OAuth infra. Both trainers and trainees have their own accounts.

When scaffolding, prefer Django's conventional project layout (`manage.py`, one `config`/project settings app, feature apps like `workouts`, `nutrition`, `accounts`) and Create React App/Vite defaults for the frontend, unless the repo already has an established structure — check first.

## Users: Trainers and Trainees

- A trainer can have multiple trainees; a trainee belongs to exactly one trainer. This is a simple one-to-many relationship — model it as a FK from trainee to trainer (`Trainee.trainer`), no join table needed.
- Both trainers and trainees log in and use the app themselves. Trainers author plans and review trainee progress/adherence; trainees log their own workout sessions and food intake.
- Workout and diet plans are **fixed and defined by the trainer** — trainees log actuals against them, they don't edit the plan itself.

## Core Features (Stage 1 scope)

### 1. Workout Tracking

- Trainer defines a **workout plan** for a trainee as a **rotation of sessions** (Session 1, Session 2, Session 3, …) — not tied to a calendar day or day of week (unlike the Diet plan's `ReferenceMeal`; see "Resolved Design Decisions"). Each `PlanSession` lists planned exercises (`PlanExercise`) with target sets, a target **rep range** (`target_reps_min`/`target_reps_max`, e.g. 8–12), and a default rest time (e.g. 120s, editable). The plan also has a target weekly frequency (`WorkoutPlan.sessions_per_week`, e.g. "3x/week") for the Progress streak.
- Trainee logs a **workout session** by picking a session — defaults to the next one in the rotation after their last completed session, but any session can be logged out of order (pure UX convenience, not enforced). The app pre-fills the prescribed exercises/sets/rep range as a template to log actuals against.
- Logging granularity is **per set**: for each exercise, log the weight used and the reps actually done in each individual set (e.g. dumbbell chest press, 3x8–12 prescribed → log weight + reps done for set 1, set 2, set 3 separately). Rest time actually taken is also logged per set (defaults to the plan's recommended rest, but editable). Each set can optionally be flagged `is_warmup` (excluded from avg-reps-per-set weight suggestions and the Progress strength score) and given an optional `rpe` (1–10) — both purely optional, never required to save a log. A session itself can carry optional free-text `notes` and an optional `duration_minutes`.
- Weight suggestions, personal-record flags, and the rest timer are computed/handled client-side from already-fetched history — no dedicated backend fields for any of them (see "Backend implementation notes (workout tab...)" below).
- Trainer-authored guidance: both `PlanSession` and `PlanExercise` carry a `notes` field the trainee sees read-only while logging (e.g. a session-wide cue like "focus on tempo this week" or a per-exercise cue like "keep your back straight") — distinct from `WorkoutSession.notes` above, which is the trainee's own reflection on a *logged* session, not trainer guidance on the *planned* one. Editable inline on Workout → Plan for trainers only (`IsTrainerWriteTraineeReadOnly`, same as the rest of plan authoring) — a narrow, notes-only slice of trainer plan-authoring UI, not the full session/exercise editor (still not built).
- Core models: `WorkoutPlan` (trainee FK, `sessions_per_week`) → `PlanSession` (plan FK, label/order, notes) → `PlanExercise` (session FK, exercise, target_sets, target_reps_min/max, default_rest_seconds, notes) → `WorkoutSession` (trainee FK, plan_session FK, date, notes, duration_minutes) → `LoggedExercise` (session FK, plan_exercise FK) → `LoggedSet` (logged_exercise FK, set_number, weight, reps_done, rest_seconds, is_warmup, rpe).

### 2. Diet Tracking

- Trainer defines a **diet plan** for a trainee as a **reference meal plan**: meals (e.g. Breakfast, Lunch, Dinner) each offering one or more named **options** (alternatives a trainee can choose between, e.g. Breakfast → "Smoothie" or "Overnight Oats"), each option containing reference ingredients with reference weights (e.g. "150g chicken breast"). A trainee picks one option per meal when logging.
- A **reference document/database** of ingredients and products (`FoodItem`) storing nutrition info per 100g (calories, macros, micros where available).
  - Stage 1: self-seeded reference table, built from whatever ingredients appear in trainers' reference meal plans.
  - Later stage: integrate a public food/barcode API (e.g. Open Food Facts) as an additional/alternative source for `FoodItem` data — same shape, so this is a swap-in, not a redesign.
- Trainee logs actual food intake **against a specific reference meal item** (e.g. "Breakfast → chicken breast") and enters the **actual weight they measured** — this is expected to differ from the reference weight (they're weighing it themselves, not aiming for exact precision).
- App **calculates**, from the actual weight logged: calories, macronutrients (protein, carbs, fat), and micronutrients (where data is available) — computed from the actual weight, not the reference weight. This gives an easy planned-vs-actual comparison for adherence tracking.
- Core models: `DietPlan` (trainee FK) → `ReferenceMeal` (diet_plan FK, label/order, optional `day_of_week`) → `MealOption` (meal FK, label, order — a named alternative, e.g. "Smoothie"; see "Backend implementation notes (meal options...)" below) → `ReferenceMealItem` (option FK, food_item FK, reference_weight_grams) → `FoodItem` (name, barcode nullable, per-100g nutrition incl. 5 micros, source: seeded/off, `kind`: single/composite, `created_by`/`visibility`/`approval_status` for the sharing model, `serving_unit`/`serving_size_grams` as an entry/display convenience, `macro_filters`/`dietary_tags` (both M2M, fixed vocab — see "Backend implementation notes (food bank filters...)" below) for substitution search — see "Backend implementation notes (food bank sharing...)" below) → `FoodItemComponent` (composite FK → FoodItem, ingredient FK → FoodItem, weight_grams — for multi-ingredient/recipe items) → `FoodLog` (trainee FK, one of `reference_meal_item`/`food_item`/`quick_log_item`, optional `logged_meal` FK grouping it into a structured day/meal-slot log, actual_weight_grams, logged_at, snapshot nutrients incl. 5 micros) → `LoggedMeal` (trainee FK, reference_meal FK, date, source: plan/custom — one per trainee/meal-slot/day; see "Backend implementation notes (meal options...)" below).
- A trainee can also log food that isn't tied to any plan: directly against a `FoodItem` (barcode/manual search) or against their own private `QuickLogItem` shortcut (e.g. "my smoothie") — see `QuickLogItem` below.
- Substitution search: a `FoodItem` can carry `macro_filters` (macro *role* - Lean Protein, Complex Carb, Fat/Oil, etc.) and `dietary_tags` (diet-type compatibility - Vegan, Keto, Gluten-Free, etc.), both fixed-vocabulary M2Ms browsable/filterable in the Food Bank UI. Each item also surfaces computed `alternatives` (other items sharing a macro filter, ranked by closeness in calories) - "what else could I eat instead of this" for when you're out of an ingredient. See "Backend/Frontend implementation notes (food bank filters...)" below.

### 3. Trainer Connection

*Not to be confused with the `TrainerConnection` model in section 7 — this section (`QAThread`/`TrainerNote`) assumes an existing trainee-trainer relationship; section 7's `TrainerConnection` is the one-time onboarding request to get one in the first place.*

- Trainee ↔ trainer Q&A: a `QAThread` (subject + status `open`/`answered`/`archived`) containing a back-and-forth of `QAMessage`s from either party. Either party can post messages, either can change the thread's status (a manual action, never an automatic side effect of replying), and either can open a new thread — a trainer opening one must name which of their trainees it's about (see "Backend implementation notes (Trainer tab — done)" below; this supersedes an earlier trainee-only restriction).
- Trainer notes: a one-way `TrainerNote` (trainer-authored, trainee-read-only) with a `read`/`read_at` flag the trainee sets via a `mark_read` action — e.g. "remember to focus on form" or "good job this week."

### 4. Exercise Bank

- A shared reference bank of exercises (`Exercise`, writable by any trainer, browsable by all trainees — same access pattern as `FoodItem`): name, description, `equipment` (freeform, e.g. "Barbell"/"Bodyweight"), `primary_muscle_groups`/`secondary_muscle_groups` (both M2M `MuscleGroup`, plain-language names — split so the muscle diagram can show primary-vs-secondary intensity), `difficulty_level` (beginner/intermediate/advanced), optional `image`, optional `video_url` (YouTube only, stored as-is), and `alternatives` (self M2M, non-symmetrical — each exercise curates its own list) for swapping out a movement when equipment is unavailable.
- `PlanExercise` (workout plans) references `Exercise` by FK rather than a freeform name, so plans are built from the bank.
- Browse UI (`Workout → Exercise Bank`, read-only for both roles — see "Frontend implementation notes" below): search + filter by muscle group and difficulty, an expandable card per exercise showing a front/back muscle-highlight diagram and its alternatives.

### 5. Daily Tracker

- `DailyMetric`: one row per trainee per day — weight (+ unit), steps, sleep hours, plus `sleep_quality` (1-5), `readiness` (1-5), `water_intake_ml`, and free-text `notes`, all optional.
- `ActivityLog`: freeform activity type (e.g. "volleyball", "tennis") + duration, multiple per day allowed, plus optional `calories_burned` (manual entry, no estimation formula) and free-text `notes`.
- A read-only dashboard endpoint aggregates `DailyMetric` and `WorkoutSession` dates over a date range for a trainee (or, for a trainer, one of their trainees).
- The Daily tab (`GET /api/tracker/daily-summary/?date=`) computes a read-side rollup for one date — calories/macros consumed (that date's Diet-tab food logs), calories burned (`ActivityLog.calories_burned` only — see "Backend implementation notes (daily tracker — done)" below for why `WorkoutSession` doesn't contribute), net balance, and the trainee's diet plan target for a planned-vs-actual comparison. Computed on request, never stored, since the underlying logs can be edited after the fact.

### 6. Settings & Personalization

- A hamburger-menu surface (`NavDrawer`) with six items: **Profile** (name, password, and — for trainees — the body stats/goals/preferences below), **Goals**, **Plan Management** (a pure navigation shortcut to Diet → Plan / Workout → Plan, not a duplicate editing surface — no trainer-side plan-authoring UI exists yet, see Build Order step 8), **Units & Preferences**, **Reminders**, **Data Export**. The earlier placeholder **Settings** entry was removed entirely — nothing in it was in use.
- `Goal`: `goal_type` (`weight`/`strength`), weight-goal fields (`target_weight`/`target_weight_unit`/`direction`) or strength-goal fields (`exercise` FK/`target_value`/`target_value_unit`), optional `target_date`, `is_active` (archive without deleting). Multiple active goals are allowed at once (a weight goal plus several independent strength goals). **Trainer-readable, trainee-writable** (`IsTraineeWriteTrainerReadOnly` + `TraineeScopedQuerysetMixin`, same as every other trainee-owned resource) — the one resource in this batch that follows that convention rather than being private, since a goal's target line is meant to show up when a trainer views that trainee's Progress tab too. A `weight` goal renders as a dashed target line on Progress → Overview's weight series; a `strength` goal renders one on that exercise's strength chart in the Training dashboard (matched by `exercise` FK). Neither goal type stores its own "starting point" — see `current_weight_kg` under Onboarding below, shared with BMI's weight resolution.
- `UserPreference` (`default_weight_unit`) and `ReminderSetting` (`reminder_type`: weight/sleep/diet_log/workout_log; `is_enabled`; `time_of_day`; four `channel_*` booleans) are **fully private to the owner** (`IsAuthenticated` + `queryset.filter(user=request.user)`, no trainer branch) — a deliberate departure from the app's usual "everything trainee-owned is trainer-readable" convention, since these are personal account settings, not training data. `ReminderSetting` upserts on `(user, reminder_type)`, same convention `DailyMetric` already established.
- `Notification` (the in-app list, and the source for a one-time login banner) and `PushSubscription` (real Web Push via `pywebpush` + dev-only VAPID keys in `config/settings.py`) back reminder delivery: `channel_in_app` always creates the row; `channel_banner` controls whether it's also queued as a banner; `channel_push` controls whether a push is actually sent. A goal-completion notification (weight/strength target reached) reuses this exact infrastructure rather than a separate path — always banners + pushes, since there's no per-goal channel config to check. Delivery fires via `usersettings/management/commands/send_due_reminders.py`, intended to run under a plain OS cron entry — no Celery/task queue yet, see Deferred.
- Data Export: three CSV endpoints (`/api/export/diet-log|workout-log|daily-metrics/`), self-only (no `trainee_id`/trainer branch — "export my own logged data"), date-range filtered, reusing the same `logged_meal__date` OR `logged_at__date` matching `DailySummaryView` already uses for ad hoc vs. structured food logs.
- Profile absorbs what would've been "Account Settings" (name, password change) plus, for trainees, onboarding-captured data that stays editable afterward — see section 7 and its own implementation notes below.

### 7. Onboarding Wizard & Initial Trainer Assignment

Not to be confused with section 3's Trainer Connection (`QAThread`/`TrainerNote`), which assumes an *existing* trainee-trainer relationship — this is the one-time flow for a brand-new trainee to request one in the first place.

- Self-service **signup** (`POST /api/auth/signup/`, public) creates a **trainee-only** account (trainers are still admin-provisioned — no self-serve trainer path, matching this app's ~10-user trust model) and returns a token, same shape as login.
- A 4-step **onboarding wizard** (`/onboarding`, distinct from the ongoing `/profile` edit surface, though they share components) walks a first-time trainee through Baseline → Goals → Preferences → Trainer Connection. Skippable/resumable, not a mandatory gate.
- Baseline: `height_cm`/`age`/`starting_weight`+unit, stored directly on `accounts.User` (not a separate Profile model, matching how `role`/`trainer` already live directly on `User`). A computed (never stored) `bmi`/`bmi_category` is returned on every `UserSerializer` read, resolved from the trainee's latest `DailyMetric` weight if one exists, else `starting_weight` — see `accounts/services.py::resolve_current_weight_kg`/`compute_bmi`, reusing `progress.services.to_kg`. That same `resolve_current_weight_kg` also backs `Goal`'s `current_weight_kg` (section 6) — one fallback rule, two consumers.
- Goals: creates ordinary `Goal` records (section 6) directly from the wizard — no separate "starting weight" field, it pulls from Baseline/the latest log via the shared resolver above.
- Preferences: `meal_preferences` (M2M to the existing `nutrition.DietaryTag` vocab) + free-text notes, and structured workout preferences — `workout_days_per_week`, `workout_session_minutes`, `gym_location`, `experience_level`, `injury_notes` (all fixed-vocabulary dropdowns except the free-text injury notes). Captured and stored only — still no dedicated trainer-facing *display* of these specific fields (see Deferred), though the trainer now has a full plan-authoring surface (section 8) that's the actual consumer these were captured for.
- Trainer Connection: `TrainerConnection` (`connection` app) — `option_selected` (`no_preference`/`specific_trainer`/`train_myself`), `requested_trainer_name` (free text, only for `specific_trainer` — no trainer directory/search exists yet), `status` (`pending_manual_assignment`/`active`/`not_applicable`), `assigned_trainer`. `train_myself` is shown disabled ("coming soon") in the UI and rejected server-side too — not built (see Deferred). Assignment is a **manual Django admin action** for Stage 1 (no auto-matching, no trainer-side accept/decline) — `TrainerConnection.save()` makes it a single action: setting `assigned_trainer` also flips `status` to `active` **and** syncs the trainee's real `User.trainer` FK (the field the rest of the app actually keys off), so an admin doesn't have to separately edit both records.

### 8. Trainer Dashboard

The trainer's actual workspace — closes the "no trainer-side plan-authoring UI" gap that was open since Build Order step 8. Not a separate app from the trainee experience, gated by role like everything else in this app.

- **Trainee roster** (`/trainees`, a trainer's home screen): every trainee assigned via `User.trainer` (not via section 7's `TrainerConnection` directly — that's the *request*, `User.trainer` is the *resolved relationship*), searchable by name, filterable by weight trend (`losing`/`gaining`/`maintaining`, derived from the two most recent `DailyMetric` weight entries, falling back to the trainee's active weight `Goal.direction` when there's too little log data), low consistency (a combined DailyMetric/WorkoutSession/food-log adherence % over a 14-day lookback), and inactivity (days since any log). All three computed in Python per-trainee (`trainerdashboard/services.py`) — a trainer's roster is small enough at this app's scale that this beats a complex ORM aggregation, matching `progress/views.py`'s existing convention.
- **Trainee detail page** (`/trainees/:id`): a Goals section (see the ownership-flip note below) plus tabs for Diet Plan, Workout Plan, Progress (read-only, exactly the trainee's own Progress tab, just scoped), and Notes & Q&A.
- **Goal ownership flips once a trainer is assigned**: a trainee may write their own goals only while `trainer` is `None` (covers section 7's onboarding wizard, used before any `TrainerConnection` resolves) — once assigned, only that trainer may write, and the trainee's own `/goals` view goes read-only. State-based (`accounts/permissions.py::GoalWritePermission`), not "goals created after assignment," so it applies retroactively to goals a trainee made before being assigned too.
- **Diet/Workout plan editing is real, full CRUD** — create/edit/delete/reorder at every level (plan → sessions/meals → exercises/options → ingredients). The backend needed no new models or permission work at all: every plan-structure viewset was already `IsTrainerWriteTraineeReadOnly` with IDOR-safe serializer querysets from the moment those apps were first built — this was purely a frontend gap. Every edit is logged to a new `PlanChangeLog` (`connection` app — `trainee`, `changed_by`, `plan_type`, `summary`), written via a small mixin rather than signals, and shown as collapsible change history at the top of each plan tab.
- **Two models the spec named collide with, but mean something different from, what was already shipped** — resolved by adding distinctly-named new pieces rather than repurposing working features: `TrainerPrivateNote` (trainer-only scratchpad, the trainee can never see it) sits alongside the existing, unrelated `TrainerNote` (trainer-authored, trainee-*readable*, its own Trainer-tab UI on both sides — section 3). The spec's flat `QAMessage` was never built — section 3's existing `QAThread`/`QAMessage` (subject, status, threading) already satisfied the actual requirement and is simply reused, scoped to one trainee via the same `?trainee_id=` filter pattern used everywhere else.

## Conventions

- Keep API endpoints RESTful and resource-oriented (e.g. `/api/workouts/sessions/`, `/api/nutrition/food-items/`, `/api/nutrition/logs/`).
- Nutrient math (scaling per-100g values by consumed weight) belongs in a model method or a small service/util function, not duplicated in views or serializers.
- Write migrations for every model change; don't hand-edit migration files.
- Prefer Django REST Framework serializers + viewsets over hand-rolled views unless there's a good reason not to.
- Keep frontend components small and feature-scoped (`WorkoutLogger`, `FoodLogEntry`, etc.) rather than one large page component.
- No auth/infra complexity beyond what ~10 users need — flag it if a request seems to be scope creep for this stage.

### Backend implementation notes (steps 1-5, done)

- Django project lives in `backend/` (not repo root): `backend/manage.py`, `backend/config/` (settings/urls), `backend/accounts/`, `backend/workouts/`, `backend/nutrition/`. Virtualenv at `backend/.venv/` (gitignored) — run tooling via `backend/.venv/bin/python manage.py ...` (activation doesn't persist across separate tool calls in this environment).
- `accounts.User` extends `AbstractUser` with `role` (`trainer`/`trainee`) and a self-referential `trainer` FK (`related_name="trainees"`, `limit_choices_to={"role": "trainer"}`). `AUTH_USER_MODEL = "accounts.User"`.
- DRF installed with `SessionAuthentication` + `TokenAuthentication` (`rest_framework.authtoken`), default permission `IsAuthenticated`. Token endpoint: `POST /api/auth/token/`.
- Full model set from the sections above is implemented as designed, with `PROTECT` on `FoodItem`/`ReferenceMealItem` FKs so historical logs can't be silently cascade-deleted.
- Nutrient scaling util: `nutrition/services.py::scale_nutrients(food_item, weight_grams)` — coerces values through `Decimal(str(...))` (raw floats assigned to `DecimalField`s aren't auto-cast and will blow up multiplication otherwise). Exposed via `FoodItem.nutrients_for_weight()`, `ReferenceMealItem.reference_nutrients()`, `FoodLog.actual_nutrients()`.
- Seed command: `python manage.py seed_food_items` (idempotent, `update_or_create` by name) — seeds ~20 common ingredients in `nutrition/management/commands/seed_food_items.py`.
- API is fully wired under `/api/`: `accounts/`, `workouts/`, `nutrition/` (see each app's `urls.py`/`views.py` for the exact resource list — matches the RESTful convention above).
- Access control (reused across all viewsets, not duplicated per-resource):
  - `accounts/permissions.py`: `IsTrainerWriteTraineeReadOnly` (plan-authoring resources) and `IsTraineeWriteTrainerReadOnly` (session/log resources) — both permit safe methods for either role and restrict writes to the appropriate role.
  - `accounts/mixins.py`: `TraineeScopedQuerysetMixin` — set `trainee_path` per viewset (e.g. `"trainee"`, `"session__trainee"`, `"day__plan__trainee"`) and it scopes the queryset to the trainer's own trainees or the trainee's own records.
  - Every writable FK field on every serializer has its `queryset` restricted in `__init__` to what the requesting user may reference (prevents IDOR — e.g. a trainee can't attach a logged set to someone else's session by guessing its ID). `trainee` on session/log serializers is server-set (`perform_create`), never trusted client input.
- Verified end-to-end with an `APIClient`-based smoke test (trainer builds a full plan → trainee logs a session set-by-set; diet plan → food log with computed nutrients; cross-trainer isolation and IDOR attempts correctly rejected). It's imperative (`createBodyHighlighter({container, ...})` mounts straight to a DOM node, returns `{update, destroy}`), so `MuscleDiagram` wraps it in the standard `useRef` + `useEffect(() => { ...; return () => instance.destroy() }, [deps])` pattern rather than a declarative component. Renders two instances side by side (`type="anterior"` and `type="posterior"`) since one exercise's muscles can span both views. Primary-vs-secondary intensity uses the library's own `frequency` field directly (`{ muscles, frequency: 2 }` for primary, `frequency: 1` for secondary, paired with a 2-color `highlightedColors` ramp) rather than any workaround. The library's fixed muscle-slug vocabulary doesn't cover our freeform `MuscleGroup` names (confirmed by testing its own `normalizeMuscle` alias resolver directly — it only catches near-exact singular/plural spelling, not synonyms like "Traps"→trapezius or "Glutes"→gluteal), so `MuscleDiagram.tsx` hand-maps all 28 seeded muscle group names to the library's slugs; a handful of intentionally-vague ones (Arms, Back, Full Body, Hip Flexors, Legs — only used by the 5 Cardio-category exercises) are left unmapped and simply don't highlight anything.
- Workout → Plan trainer-authoring UI is not built (same situation as Diet → Plan's trainer-authoring side) — the sample plan in the dev DB was created via a management command, not through the app.

### Frontend implementation notes (workout tab → Log — done, UI reworked after initial build per user feedback)

- `WorkoutLogPage.tsx` fetches the plan + the trainee's full session history once; `lib/workoutRotation.ts::nextSessionInRotation` picks the default session (the one after whichever was most recently logged, wrapping around) - purely client-side, no backend involvement, mirrors how Diet Progress computes date ranges client-side.

This is real, persisted ordering via the already-existing `LoggedExercise.order` field (from the Phase B backend build), not just a display trick: `SessionLogForm` tracks an `exerciseOrder: number[]` array (initialized from the plan's order, or from the existing log's saved order when editing), and Save sends each exercise's current position as its `order`.
- `lib/weightSuggestion.ts::suggestWeight` takes the *plan's own* `target_reps_min`/`target_reps_max` (a later fix - it originally used a hardcoded 8–12 for every exercise, which was silently wrong for anything with a different prescribed range, e.g. a 12–15-rep accessory move; verified against real seeded history that the fix changes the actual suggested status, not just the copy). `weightDirectionFeedback` adds a second, independent piece of feedback: rather than a static red/green tied to *which way* the suggestion points, each working-set weight input is tinted live against what's actually being typed - if the suggestion says lower and you type the same-or-higher weight it stays red with a "not lower than last time" note; type something lower and it turns green ("lowering the weight - that's what's suggested"); the reverse for a "raise" suggestion. ### Backend implementation notes (Progress tab — done)

- New `progress` Django app, `/api/progress/`: six read-only `APIView`s, no new models (confirmed by `DATA_MODELS_AND_ROADMAP.md`'s own note that the Progress dashboard is "a query," not a table) — `overview`, `training`, `training-volume`, `nutrition`, `recovery`, `consistency`. - `progress/services.py` (mirrors `nutrition/services.py`'s role): `to_kg(value, unit)` — no weight-unit conversion helper existed anywhere before this; both `DailyMetric.weight` and `LoggedSet.weight` are per-row kg/lb, so anything summing/charting weight across rows needs one. `food_logs_by_day(trainee, start, end)` generalizes `DailySummaryView`'s single-date `FoodLog` OR-matching (`logged_meal__date` vs. `logged_at__date` for ad hoc logs) to a whole range, grouping in Python and running `sum_nutrients` per day — shared by `overview` and `nutrition` so the two endpoints can't disagree on which day a `FoodLog` belongs to. `diet_adherence_pct` and `monday_of` (Python equivalent of `workoutStreak.ts`'s client-side `mondayOf`, kept conceptually identical so this dashboard's week boundaries never disagree with Workout → Progress's existing streak) round out the shared helpers.

- `training` deliberately does **not** return per-set history or PR events — the frontend already has `GET /workouts/logged-sets/?exercise=&start=&end=` (lightly extended, see below) backing `ExerciseHistoryChart`/`ExerciseHistoryContent`, and PR detection is explicitly a client-side-only concern elsewhere in this app (see workout tab → Log notes below) — a second endpoint returning the same rows, or porting PR comparison logic to Python, would just be duplication with drift risk. `training`'s only job is resolving the default exercise (most-logged **in the selected range**, via `LoggedSet` `Count` + `order_by("-set_count")`) and the range-scoped picker list.
- `training-volume` buckets in Python (`sum(to_kg(weight,unit) * reps_done)` per ISO week, plus a session count) rather than an ORM `TruncWeek` annotation, specifically so the Monday-of-week definition is bit-for-bit identical to the frontend's own.
- `consistency`'s `current_streak_days` is walked backward from `min(end, today)` **unbounded by the selected range's `start`** (a fixed 365-day lookback window instead) — a "current streak" is a point-in-time fact, and bounding it by the range would silently truncate a real streak just because someone picked "Last 7 days."
- One small additive change to an existing endpoint: `frontend/src/api/loggedSets.ts::listExerciseHistory` gained an optional `range` param (forwarded to `LoggedSetViewSet`'s already-existing `?start=&end=` filters, which had no frontend caller before this) — existing callers pass nothing and are unaffected.

Intended to run every few minutes via a plain OS cron entry — **no Celery/task queue yet**, see Deferred for the planned replacement.
- `Goal.completion_notified_at` dedupes the "goal reached" check (`usersettings/services.py::check_goal_completions`, called at the end of `send_due_reminders`) so it only fires once per goal, ever — goals stay active indefinitely once reached (no auto-archive), per spec. Weight-goal "reached" compares the resolved current weight (see section 7's `resolve_current_weight_kg`) against `target_weight` by `direction` (`lose`: ≤, `gain`: ≥, `maintain`: within a **1kg tolerance — an assumption, since the spec didn't define one**). Strength-goal "reached" compares the best (max) non-warmup `LoggedSet.weight` for that `exercise` against `target_value`.
- CSV export views (`dataexport/views.py`) use the stdlib `csv` module (already this codebase's convention — `seed_food_items` reads CSV the same way) and reuse `tracker.views._parse_date` for `?start=&end=`. No serializers — rows are written directly from querysets, matching how `progress`'s aggregation views skip serializers too.

## Resolved Design Decisions

These were previously open questions, now settled:

- Workout plan structure: a rotation of sessions (Session 1, 2, 3, …), each with a fixed list of exercises/sets/target rep range, authored by the trainer. Sessions rotate rather than repeat on fixed calendar days — deliberately *not* the same model as the Diet plan's day-of-week `ReferenceMeal` (see below). Superseded an earlier "fixed weekly schedule of days" decision once the workout tab's actual spec arrived.
- Reps/weight granularity: logged per set, not per exercise.
- Diet plan scope: a reference meal plan (specific meals + ingredients + reference weights), not calorie/macro targets.
- Barcode/food data source: self-seeded reference table for Stage 1; Open Food Facts API integration planned for a later stage.
- Trainee accounts: trainees have their own logins and log their own data (not entered by the trainer on their behalf).
- Food log linkage: `FoodLog` can link to a `ReferenceMealItem` (planned adherence), a raw `FoodItem` (barcode/manual, not tied to a plan), or a `QuickLogItem` (private per-trainee shortcut) — exactly one of the three, enforced in the serializer and in `FoodLog.clean()`. Nutrients are computed once at save time and stored as a snapshot on the row, so later edits to a `FoodItem`/`QuickLogItem` don't retroactively change historical logs.
- Workout session linkage: `WorkoutSession` ties to a specific `PlanSession`, which pre-fills the prescribed template to log actuals against. Defaults to the next session in the rotation after the trainee's last logged one, but any session can be logged out of order.
- `QuickLogItem` is **private to its owner** for Stage 1 — no sharing/moderation. See **Deferred** below. (`FoodItem` got its own, separate private/public + approval model instead — see the Food Bank sharing decision below — but `QuickLogItem` itself is unchanged.)
- `day_of_week` (nullable, `null` = "applies every day") is used on `ReferenceMeal` (Diet) for weekday/weekend/fixed-daily schedules — no separate boolean (`workouts.DayOfWeek` choices, imported into `nutrition`). The Workout plan's `PlanSession` deliberately does **not** have this field: workout sessions rotate rather than repeat on fixed weekdays, so the two plan types now genuinely diverge instead of sharing one convention (this used to be identical on both; see the workout plan structure decision above).
- Exercise bank writes follow the same trust model as `FoodItem`: any trainer can add/edit (shared reference data, not trainee-scoped); all trainees get read access.
- Trainer connection (`connection` app): `QAThread`/`QAMessage` use plain `IsAuthenticated` + queryset scoping (both roles read/write within their own relationship) rather than an asymmetric permission class, since both parties post messages; `TrainerNote` stays asymmetric (trainer writes, trainee read-only + a dedicated `mark_read` action).
- `QAThread` creation: either role can open a new thread (not trainee-only, as originally decided — revisited per explicit user request when building the Trainer tab UI). A trainer must name which of their own trainees the thread is about; a trainee's thread is always about themselves, server-set. Thread status changes are always a manual, explicit action by either party — never an automatic side effect of posting a reply.
- `TrainerNote` read state: marked read automatically as soon as the trainee opens the Trainer tab's Notes view (not only via an explicit "mark read" tap) — behaves like a normal notification inbox.
- Daily tracker (`tracker` app): `DailyMetric` is `unique_together(trainee, date)` — one row per trainee per day; `ActivityLog` allows multiple rows per day. The dashboard is a plain aggregation endpoint (`GET /api/tracker/dashboard/`), not a model.
- Water intake (`DailyMetric.water_intake_ml`) is stored as whole milliliters — the app had no existing volume-unit convention to follow (unlike weight's `kg`/`lb`), so this introduces the simplest possible one rather than adding a unit picker.
- Calories burned for the Daily tab's rollup comes from `ActivityLog.calories_burned` (manual entry) only — `WorkoutSession` carries no calorie field in Stage 1 and there's no estimation formula for either, so a trainee's logged workouts don't currently count toward "calories out."
- Activity type (`ActivityLog.activity_type`) stays free text for Stage 1, per the spec's own recommendation — no seeded activity table, keeps entry frictionless; revisit if activity-level analytics (e.g. "total swim minutes this month") are wanted later, which would favor a fixed enum or lookup table.
- No edit lock on backdated `DailyMetric`/`ActivityLog` entries for Stage 1 — both stay editable indefinitely; revisit only if data integrity becomes an issue with ~10 users.
- Frontend stack: TypeScript (not JS), Vite dev-server proxy to Django (not `django-cors-headers`), auth token in `localStorage` — confirmed with the user at the start of frontend work. Tailwind CSS v4 + shadcn/ui (Radix base, "Nova" preset) was later confirmed as the app-wide design system, restyling everything already built in the same pass rather than only new components.
- Food Bank sharing model: a trainee can add `FoodItem`s directly (not just via their private `QuickLogItem`s) — private items are visible only to their creator and need no approval; public items need approval from **any** trainer (not just the trainee's own trainer) before anyone else sees them, matching `FoodItem`'s existing "shared reference data" trust model (same as the exercise bank).
- Multi-ingredient ("composite") `FoodItem`s: an item can be `kind=composite`, built from other `FoodItem`s by weight (`FoodItemComponent`) instead of manually-entered macros; its per-100g nutrition is computed automatically from its components and recomputed whenever they change.
- Serving/measurement units (`serving_unit` + `serving_size_grams` on `FoodItem`) are an entry/display convenience only, not a new logging unit — a contributor can enter nutrition label values in whatever unit is convenient (e.g. "170g serving") and the app converts to per-100g at save time, but canonical storage and all downstream scaling math (logging, composites) remain per-100g/grams throughout the app.
- Reference meal plans support **options**: a `ReferenceMeal` (e.g. Breakfast) can offer several named `MealOption` alternatives (e.g. "Smoothie" vs. "Overnight Oats"), each with its own ingredients — a trainee picks one option per meal, not a combination of several.
- Structured meal logging (`LoggedMeal`): one log per trainee per meal slot per day (`unique_together(trainee, reference_meal, date)`) — re-logging a meal the same day replaces it rather than creating a second entry (no "second breakfast" support yet). Each log's `source` is `plan` (chosen option, weights freely editable from the reference) or `custom` (a deliberate whole-meal, off-plan swap built from the food bank) — never a mix of the two within one logged meal.
- Structured workout session logging (`WorkoutSession`): one log per trainee per plan session per day (`unique_together(trainee, plan_session, date)`) — re-logging the same session the same day replaces it, same convention as `LoggedMeal`. PR detection, weight suggestions, and the rest timer are all computed/handled client-side from already-fetched history, not stored fields — see "Backend/Frontend implementation notes (workout tab → Log...)".
- Food Bank substitution search: a fixed vocabulary of `MacroFilter`s (macro role) and `DietaryTag`s (diet-type compatibility), both hand/heuristic-classified for the existing seeded reference table since trainers/trainees pick them by hand only for items they add themselves going forward. Alternatives are computed **live at request time** from shared `macro_filters` + closeness in calories, not stored - unlike `Exercise.alternatives`, which *is* a stored, curated self-M2M, because Exercise Bank fetches its whole ~100-row list once (cheap to resolve alternatives client-side from what's already in memory) while Food Bank items are searched/paginated (no such in-memory list to resolve against).
- Workout Log's per-set entry is **one set at a time, not a flat form**: fill a set's weight/reps, confirm, it collapses to a summary line, the next set's inputs appear - reflecting that a trainee physically can't do set 2 before set 1 and that seeing every set's inputs simultaneously read as overwhelming. Warm-up sets are a separate section above working sets (their own "+ Add warm-up set" affordance), not a per-row toggle mixed into the working sets. Exercise cards are an accordion (only one open at a time, owned by the parent form, not each card) rather than independently-collapsible, specifically so reordering exercises can't shuffle an already-expanded neighbor into view and read as an accidental uncollapse. Exercise order within a logged session is trainee-editable (up/down, persisted via the existing `LoggedExercise.order`) for "someone's using that machine" swaps.
- Weight suggestions compare against the *plan's own* prescribed rep range (`PlanExercise.target_reps_min`/`max`), never a fixed 8–12 - and the weight-input color is **direction-following**, not status-static: it tracks whether the currently-typed weight actually follows the suggestion (lower than last time when told to lower, higher when told to raise), not just which direction the suggestion happens to point.
- The Progress tab's six `/api/progress/` endpoints are pure aggregation over existing resources - no new models, same as the roadmap doc's own "no new table needed, this is a query" call. PR events for its Training dashboard are computed **client-side** (reusing the existing `checkPersonalRecord` comparison via a new chronological-replay function) rather than by the backend, consistent with PR detection already being a deliberate client-only concern elsewhere in the app. The overview chart's n-axis SVG (extending the exercise-history chart's dual-axis pattern) was chosen over introducing a charting library, to stay consistent with every other chart in the app. The Photos section is a placeholder for this pass - `ProgressPhoto` stays deferred (see "Deferred" below).
- Reminder/goal-completion delivery runs off a plain-cron `send_due_reminders` management command (real Web Push via `pywebpush`, no stub), not a task queue — chosen deliberately over Celery/Redis to avoid adding new services to run/deploy at this app's ~10-user scale. **A full task queue is the intended eventual replacement once cron-based firing isn't precise/reliable enough** (see Deferred). Reminder/goal-completion notifications ship with in-app, push, and login-banner channels in Stage 1; `channel_email` is a real, saved toggle already visible in the Reminders UI but inert until email delivery is built (see Deferred).
- Goals stay active indefinitely once reached — no auto-archive or completion prompt in Stage 1, just a one-time `Notification` via `Goal.completion_notified_at`. Deciding between auto-archive, a prompt-to-close, or a persistent "reached" indicator is deferred (see Deferred).
- `Goal` was originally trainer-readable/trainee-writable (same `IsTraineeWriteTrainerReadOnly` pattern as everything else) so a goal's target line would show up on a trainer's view of that trainee's Progress tab. **Superseded by the Trainer Dashboard build**: ownership now flips once a trainer is assigned — see below. `UserPreference` and `ReminderSetting` remain **fully private to the owner** — the first resources in this app with no trainer branch at all — since they're personal account settings, not training data a trainer has reason to see.
- Height is stored as a single canonical `height_cm`, no stored unit field — the frontend's cm/ft+in toggle is an entry convenience only, mirroring `FoodItem.serving_unit`/`serving_size_grams`'s existing precedent rather than adding a new stored-unit column the way weight already has one.
- Onboarding is a **dedicated wizard** (`/onboarding`), separate from the ongoing `/profile` edit surface — not just extra fields bolted onto Profile. The two share components (`BodyForm`/`GoalsOnboardingCard`/`PreferencesForm`) so they can't drift apart, but the wizard is what a first-time trainee is routed to (via `IndexRedirect`), while Profile stays the "come back and edit any of this later" surface. Skippable/resumable, never a mandatory gate.
- Signup is **trainee-only self-service** (`POST /api/auth/signup/`); trainers are still provisioned by an admin, matching the existing dev-only user-creation convention and this app's ~10-user trust model — there's no self-serve "become a trainer" path and none is planned.
- `TrainerConnection` assignment is a **manual Django admin action** for Stage 1 — no automated matching, no trainer-side accept/decline. Setting `assigned_trainer` on the record automatically syncs the real `Trainee.trainer` FK and flips `status` to `active` in one step (via a `save()` override), rather than requiring an admin to separately edit two different records to make an assignment actually take effect.
- **`Goal` ownership flips once a trainer is assigned** (Trainer Dashboard build, supersedes the earlier trainer-readable/trainee-writable decision above): a trainee can write their own goals only while unassigned (`trainer_id is None` — covers the onboarding wizard, used before any `TrainerConnection` resolves); once assigned, only that trainer may write, and the trainee's own `/goals` view goes read-only. State-based, so it applies retroactively to goals a trainee made before being assigned, not just ones created afterward.
- Diet/Workout plan editing is trainer-only, full CRUD, built directly on top of already-existing (not newly added) backend write permissions — the gap closed here was entirely a frontend one. Every edit is logged (`PlanChangeLog`) rather than offering real version history/diffing — "so the trainer has a record without needing to compare versions manually" (the spec's own words) is satisfied by a chronological summary list, not a full diff view.
- Two spec-named models collided with, but meant something different from, already-shipped features — resolved by adding new, distinctly-named pieces rather than repurposing working ones: `TrainerPrivateNote` (new, trainer-only) sits alongside the unrelated, trainee-visible `TrainerNote` (existing); the spec's flat `QAMessage` was never built since the existing `QAThread`/`QAMessage` (subject, status, threading) already satisfied the actual requirement and was reused as-is, just scoped with a new `?trainee_id=` filter.
- The Trainer Dashboard's `/api/trainer/` prefix is used for exactly one genuinely new endpoint (the trainee roster with computed trend/consistency/inactivity). Every other capability the spec described under that same prefix is the frontend composing/reusing endpoints that already lived in their own resource's app (`/api/accounts/trainees/{id}/`, `/api/goals/`, `/api/connection/private-notes/`, `/api/connection/threads/`) rather than adding parallel duplicate routes.

## Deferred (not built yet — don't forget)

- **Public/shared `QuickLogItem`s**: an `availability` (`private`/`public`) + `approval_status` (`pending`/`approved`/`rejected`) moderation workflow so a trainee's saved shortcut can be shared community-wide after admin approval. Skipped for Stage 1 (10 users, private-only is enough); revisit if trainees start asking to share shortcuts.
- **`ProgressPhoto`**: a dated progress-photo model (optionally linked to a `WorkoutSession`), feeding into the dashboard. Skipped for Stage 1. The Progress tab's dashboard endpoints/UI are now built (see "Backend/Frontend implementation notes (Progress tab...)" above) with a placeholder "Coming soon" Photos section waiting for this — add the model, an upload endpoint/UI, a chronological timeline, and a before/after compare view when wanted.
- **Measurement-unit picker in the composite ingredient-builder's inline "add new ingredient" form**: currently grams/100g-only there; the full Measurement picker only lives in the main Add Food dialog. Add if it turns out to be a common friction point.
- **Full task queue (Celery + Redis + celery-beat) for reminders/goal-completion delivery**, replacing the current plain-cron `send_due_reminders` management command, once precise/reliable-enough scheduling matters more than avoiding new services to run/deploy.
- **Email delivery for reminders and goal-completion notifications** — `channel_email` is a real, saved toggle already visible in the Reminders UI, but delivery is inert until this is built.
- **A trainer-facing view of a trainee's `meal_preferences`/workout preferences/`injury_notes`** — captured and stored on `User` during onboarding, still not surfaced anywhere in the UI a trainer actually uses (including the now-built Diet/Workout plan editors in the Trainer Dashboard — they don't show these fields anywhere yet, even though they're the natural place for them).
- **"Train myself" mode** (`TrainerConnection.Option.TRAIN_MYSELF`) — logging-only, no trainer relationship. Shown disabled ("coming soon") in the onboarding wizard and rejected server-side; not built.
- **A trainer directory with search**, so a "specific trainer" `TrainerConnection` request can be validated against a real trainer record instead of stored as free-text `requested_trainer_name`.
- **Automatic trainer matching** for `no_preference` `TrainerConnection` requests (by specialty, goal type, or availability), replacing today's fully-manual Django-admin assignment, once user count justifies it.
- **A pending/accept workflow for trainer assignment** — today, an admin setting `TrainerConnection.assigned_trainer` is final and immediate (it directly sets `Trainee.trainer`); there's no step for the assigned trainer to confirm or decline first.
- **Decide goal completion handling long-term**: auto-archive, a prompt-to-close, or a persistent "reached" indicator on the goal — today a completed goal just stays active forever with a one-time notification (`Goal.completion_notified_at`) and no other UI change.
- **A trainee-facing view of `PlanChangeLog`** — currently trainer-only (`IsTrainer`); a trainee might reasonably want to see "my trainer updated my workout plan on Sep 3" too, but the spec framed this as a trainer's own record-keeping tool, so it wasn't built for the trainee side.
- **Real version diffing for plan changes** — `PlanChangeLog` is a one-line chronological summary per edit ("Added session 'Push Day'"), not a snapshot/diff of what the plan looked like before vs. after. Fine for "did something change and when," not for "exactly what changed."
- **Drag-and-drop reordering** in the Diet/Workout plan editors and the trainee roster's filters — reordering is up/down chevrons only (two `PATCH`es swapping `order`), matching `ExerciseLogBlock.tsx`'s existing convention rather than adding a drag library.
