# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project Overview

Rejim is an application for tracking workouts and diet, built around a **trainer/trainee** relationship: a trainer authors fixed workout and diet plans for each of their trainees, and trainees log their actual sessions/food against those plans. Stage 1 targets a small group (~10 users) — favor the simplest correct Django/React implementation over speculative scale, abstraction, or infrastructure. Scalability is a future concern, not a Stage 1 one.

## Tech Stack

- **Backend:** Django + Django REST Framework, in `backend/` (`manage.py`, `config/` settings, feature apps: `accounts`, `workouts`, `nutrition`, `connection`, `tracker`, `progress`, `usersettings`, `dataexport`, `trainerdashboard`). Virtualenv at `backend/.venv/` (gitignored) — run tooling via `backend/.venv/bin/python manage.py ...`.
- **Frontend:** React + TypeScript, Vite, in `frontend/`. Tailwind CSS v4 + shadcn/ui (Radix base, "Nova" preset, brand purple `#4c236b`). Dev server proxies `/api` → `localhost:8000` (no CORS package needed).
- **Database:** SQLite for local dev; Postgres in production.
- **Auth:** DRF token auth (`rest_framework.authtoken`), token kept in `localStorage`. Two dev accounts live directly in the gitignored `db.sqlite3`: `trainer1`/`devpass123`, `trainee1`/`devpass123` (trainee1's trainer = trainer1) — recreate manually if the DB is ever reset.

## Users: Trainers and Trainees

- Independent `is_trainee`/`is_trainer` booleans on `accounts.User` (not a single `role` field) — a dual-role account (e.g. a trainer who also logs their own training) is fully supported. `Trainee.trainer` is a simple FK; a trainee has at most one trainer at a time.
- Plans (workout/diet) are authored by the trainer; trainees log actuals against them and never edit the plan structure itself.
- **Login is a two-door pattern**: the primary card is trainee login/signup; `?as=trainer` swaps to a login-only "Are you a trainer?" door (same credentials — trainers are still admin-provisioned, no self-serve trainer signup). Which door was used only picks the initial `viewMode`/landing dashboard, silently corrected if it doesn't match the account's actual flags. `viewMode` persists in `localStorage` and is switchable in-session (a dual-role account gets a quiet nav link both ways). While `viewMode === 'trainer'`, nav is trimmed to what a trainer actually needs: `BottomNav` shows three tabs — Food Bank and Exercise Bank flanking an emphasized, centered Trainees tab (the trainer's home) — and `NavDrawer` collapses to just Profile, since the trainee-only tabs/settings don't apply. Food Bank/Exercise Bank are reached via unguarded top-level routes (`/food-bank`, `/exercise-bank`) that reuse the same `FoodBankPage`/`ExerciseBankPage` components trainees reach at `/diet/food-bank`/`/workout/exercises` — both are shared reference data (any trainer can write, everyone can read), so there's no trainee/trainer-specific variant to maintain.
- Shared access-control building blocks (reused across nearly every viewset, don't duplicate): `IsTrainerWriteTraineeReadOnly` / `IsTraineeWriteTrainerReadOnly` / `EditRequestPermission` (`accounts/permissions.py`), `TraineeScopedQuerysetMixin` (`accounts/mixins.py` — scopes a queryset via a per-viewset `trainee_path`), and IDOR-safe serializers (every writable FK's queryset restricted in `__init__` to what the requester may actually reference). Where a request is ambiguous between "act as myself" and "act on a named trainee" (only possible because of dual-role accounts), the rule is **explicit-target presence**: an explicit `?trainee_id=`/`trainee` field means "for that trainee" (validated against the requester's own trainees); omitting it means "for myself." This only applies to list/create, though — retrieve/update/partial_update/destroy skip the branching entirely and match either capacity (own record, or a trainee's as their trainer), since the pk in the URL already pins the object and there's nothing left to disambiguate; every trainer-dashboard by-id call (edit, delete, reorder) relies on this rather than passing `trainee_id`.

## Core Features

### 1. Workout Tracking
`WorkoutPlan` (trainee, `sessions_per_week`) → `PlanSession` (label/order — a **rotation**, not a calendar day; notes) → `PlanExercise` (FK `Exercise`, target_sets, target_reps_min/max, default_rest_seconds, notes, `superset_with` — see below) → `WorkoutSession` (trainee, plan_session, date, notes, duration_minutes, `calories_burned` — optional, device-reported, e.g. from a watch; a per-session detail only, not summed into the Daily Tracker's "calories out" total, see section 5; `unique_together(trainee, plan_session, date)` — re-logging replaces) → `LoggedExercise` (order, `substituted_exercise`, `superset_partner` — see below) → `LoggedSet` (weight, reps_done, rest_seconds, is_warmup, is_dropset, rpe 1–10).
- **A logged history record must never be destroyed by a later plan edit.** `WorkoutSession.plan_session` and `LoggedExercise.plan_exercise` are both `on_delete=SET_NULL` (not `CASCADE`) precisely so a trainer reshaping a trainee's plan — deleting a `PlanSession`/`PlanExercise` to replace it with something different, e.g. moving them to a totally different program — never cascades into deleting what the trainee already logged against it. What breaks instead of the row itself is just the *live* FK: `plan_session`/`plan_exercise` come back `null` on an orphaned row (frontend types reflect this — `WorkoutSessionLog.plan_session`/`LoggedExerciseEntry.plan_exercise` are `number | null`), while `WorkoutSession.plan_session_label` and `LoggedExercise.planned_exercise` are snapshots taken at save time (refreshed on every re-save while the plan_session/plan_exercise is still live, in `WorkoutSessionSerializer._upsert`) that keep `plan_session_label`/`exercise_name` resolving correctly forever after — Session History, Exercise History (`?exercise=` filtering), and the workout CSV export all read through these snapshots rather than the live relation for exactly this reason. `LoggedExercise.superset_partner` already had this right (`SET_NULL`) before this fix; `plan_session`/`plan_exercise` didn't. One more piece: if a *sibling* logged exercise in the same session gets orphaned this way while the session itself stays live, `WorkoutSessionSerializer._upsert` only replaces `logged_exercises` with a live `plan_exercise` on a resave (`.filter(plan_exercise__isnull=False).delete()`, not `.all().delete()`) — the frontend's live-plan-driven editing form can't represent an orphaned entry to resubmit it, so its *absence* from a resave means "wasn't editable," not "trainee removed it," and `SessionLogForm.tsx` excludes it from the editable reconstruction accordingly (`editableLoggedExercises`) while it stays fully visible, untouched, in read-only history.
- Logging is per-set, one set revealed at a time (you can't do set 2 before set 1); warm-ups are their own section above working sets. `SessionLogForm.tsx` (the session log page) is an overview list of collapsed exercise/superset rows (`ExerciseLogListRow.tsx`/`SupersetLogListRow.tsx` — name, info icon, set/round summary, up/down reorder chevrons in reorder mode); tapping a row's **Log exercise(s)** button swaps the whole page to a full-screen logging view for just that exercise/pair (`ExerciseLogBlock.tsx`/`SupersetLogBlock.tsx`, now content-only) via a `focusedPeId` state swap — not a route, no URL change, but the same sticky back-button header pattern as `LogMealPage` — replacing an earlier inline-accordion design that got clumsy once a weight-unit picker and history link were duplicated per exercise. A page-level weight-unit (lb/kg) toggle now lives once at the top of the overview list instead (with a link to Unit Preferences). Within the full-screen view, `ExerciseHistoryDisclosure.tsx` is a collapsible "History" card (closed by default; for a superset it stacks both exercises' history under their own name) — **not** `ExerciseHistoryCard.tsx`, an unrelated pre-existing component (the Progress tab's "search any logged exercise" card) that shares a similar name; a past session accidentally overwrote it by reusing that filename, so double-check before creating a new `workout/` component whose name might already exist. The exercise name in a log row/view is plain text with a dedicated info icon (ⓘ) next to it to open the exercise-detail popup — the name itself isn't a click target, so "view info" and "expand to log" don't compete on the same tap. The RPE picker in each set row (`SetRows.tsx`) has the same ⓘ pattern next to it, opening `RpeInfoDialog` (static content: what RPE means, plus what each of the four `lib/rpe.ts::RPE_OPTIONS` labels corresponds to) — most trainees know the acronym but not how to map a set to a number.
- Weight suggestions, PR detection, and the rest timer are all **client-side only**, computed from an already-fetched `GET .../logged-sets/?exercise=` history — no backend fields/endpoints for any of it.
- **In-progress session logging survives the app being closed/killed mid-session** (`lib/workoutDraft.ts` + `SessionLogForm.tsx`): a full session can take an hour or more, but `SessionLogForm` only ever talks to the backend once, on "Save log" - everything up to that point used to live in React state alone, gone the moment iOS reclaimed the tab or the phone died. Every change (a confirmed set, notes, duration, overrides, reordering) is now mirrored into `localStorage`, keyed by `(plan_session, date)` - the same identity `WorkoutSession` itself upserts on. Opening the log page checks for a matching draft first and, if found, restores it (winning over both a blank form and an already-saved log, including re-opening an existing log to tweak it further) and shows "Restored your unsaved changes from before."; cleared as soon as a save actually succeeds or an existing log is removed.
  - The tricky part was avoiding two failure modes, not the storage itself: (1) writing back a no-op "echo" of data the restoration effect *just* mechanically set, most importantly right after a successful save (which feeds the saved log back in as `existingLog`, re-running that same restoration effect - comparing the echoed data's own content isn't reliable here since the backend can return it reformatted, e.g. `"135"` → `"135.00"`) - solved with a `restoreGeneration` counter, bumped as *state* (batched together with the restored data in the very same render, unlike a plain ref flag) so the persistence effect can tell "this render's data is still exactly what was just restored" apart from a genuine edit; and (2) React StrictMode's dev-only double-invocation of mount effects, which independently produces a spurious *empty* write before the counter above even has a chance to settle - `saveWorkoutDraft` treats a content-less candidate (no set anywhere has anything entered, no notes/duration/overrides either) as a no-op rather than a write, which incidentally also means a genuinely still-blank session's defaults never get persisted as if they were unsaved changes in the first place.
- **`RestTimer`'s completion alert** (three Web Audio beeps + `navigator.vibrate` where supported) creates/resumes its `AudioContext` synchronously inside the "Start rest" tap handler and keeps it in a ref for the whole rest period, rather than creating it inside the `setTimeout` callback that fires when the countdown reaches zero — iOS Safari (this app's primary target) only lets an `AudioContext` actually produce sound if it was created/resumed inside a real user-gesture handler; one created later runs without error but stays silently muted. Any future change to this component's audio has to keep that context creation on the click itself.
- `PlanSession.notes`/`PlanExercise.notes` are trainer guidance, shown read-only to the trainee while logging; trainer-editable inline on Workout → Plan.
- **Supersets** (trainer-authored default): `PlanExercise.superset_with` is a symmetric self-FK — pairs only (not trisets+), always mirrored on both sides by `PlanExerciseViewSet`'s trainer-only `pair`/`unpair` actions (`SessionEditor`'s per-row "Superset options" dropdown auto-unpairs any stale previous partner first). Logging renders a paired PlanExercise pair as one merged `SupersetLogBlock`: warm-ups stay independent per exercise (rendered stacked — each exercise's own name, then its warm-up sets, then its own "Add warm-up set", one below the other — not a side-by-side 2-column grid, which cramped each set-editor row on a phone), but working sets become **rounds** — one combined editor for both exercises' weight/reps/RPE with a single "Confirm round" button and no rest in between, then one shared rest timer (defaulting to the longer of the two configured rest periods). This needs no `LoggedExercise`/`LoggedSet` schema at all — saving still produces two ordinary `LoggedExercise` rows with matching `set_number`s per round, same "client-side-only" spirit as weight suggestions/PR detection/rest timer above.
- **Off-program exercise + per-log superset override** (trainee-only, via the "Off-program exercise" button/dialog below "Reorder exercises" in Log): lets a trainee adjust *today's log only*, never the plan itself. `LoggedExercise.substituted_exercise` (FK `Exercise`, nullable) swaps in a different exercise while keeping the plan's own target sets/reps/rest (e.g. usual equipment unavailable); `LoggedExercise.superset_partner` (FK `PlanExercise`, nullable) ad hoc pairs/unpairs any two of today's exercises as a superset regardless of the plan's own `PlanExercise.superset_with` — the frontend always resolves and saves the *effective* value (falling back to the plan default when untouched), so a saved log is never ambiguous. History (`GET .../logged-sets/?exercise=`) and PR detection follow the substituted exercise, not the planned one, once one was logged (`LoggedSetSerializer.get_exercise`/`LoggedExerciseNestedSerializer.get_exercise_name`). `lib/exerciseOverrides.ts` centralizes the effective-value/pair/unpair logic shared between the dialog and the log form's block-grouping.
- **Per-side (unilateral) exercises**: `Exercise.is_unilateral` (e.g. Single-Arm Dumbbell Row, Bulgarian Split Squat — hand-flagged in `seed_exercises`' `UNILATERAL` set, same pattern as its `ADVANCED`/`BEGINNER` difficulty sets; editable via the Exercise Bank's add/edit dialog, a `Switch`). `LoggedSet.weight`/`reps_done`/`rpe` are nullable and used only for a normal (bilateral) set; a unilateral one instead fills `weight_left`/`weight_right`/`reps_done_left`/`reps_done_right`/`rpe_left`/`rpe_right` — never both shapes at once, enforced (validated and written) by `WorkoutSessionSerializer` against the logged exercise's *effective* exercise (respecting an off-program substitution, same resolution as above). Logging (`SetRows`/`ExerciseLogBlock`/`SupersetLogBlock`) renders two Weight/Reps/RPE rows (L/R) instead of one whenever the effective exercise is unilateral. Weight suggestions, PR detection, and the exercise-history chart don't reason about per-side data yet — they explicitly exclude a unilateral exercise's sets (`lib/personalRecord.ts`/`lib/weightSuggestion.ts`; `ExerciseHistoryContent` skips rendering `ExerciseHistoryChart` once a history is all-unilateral) rather than compute something misleading; the plain history list, Session History, and the workout CSV export all show the real per-side values.

### 2. Diet Tracking
`DietPlan` (trainee) → `ReferenceMeal` (label/order, optional `day_of_week`) → `MealOption` (a named alternative, e.g. "Smoothie" vs. "Overnight Oats") → `ReferenceMealItem` (FK `FoodItem`, reference_weight_grams). `FoodItem` (per-100g nutrition incl. 5 micros; `kind` single/composite; `created_by`/`visibility`/`approval_status` for sharing; `macro_filters`/`dietary_tags` M2Ms, fixed vocab, for substitution search) → `FoodItemMeasure` (food-specific named units this item can be logged in — label, `grams_per_unit`, at most one `is_default` per item — e.g. "tbsp", "whole (thigh)", "cup (chopped)", on top of the universal g/oz/lb weight units every item gets for free; see `lib/servingUnits.ts`) → `FoodItemComponent` (composite ingredient breakdown) → `FoodLog` (trainee; exactly one of `reference_meal_item`/`food_item`/`quick_log_item`, *or* none of the three plus a `custom_name` — see custom meals below; optional `logged_meal` FK; nutrients snapshotted at save time so later edits to a `FoodItem` don't retroactively change history) → `LoggedMeal` (trainee, reference_meal, date, source plan/custom; `unique_together` — re-logging replaces).
- A trainee logs against a specific reference item and enters the actual amount measured in grams/oz/lb or any of that item's own `FoodItemMeasure`s — `lib/servingUnits.ts::availableUnits`/`gramsForQuantity` do the conversion, used identically for a plan-sourced item (`ReferenceMealItemDetail.food_item_measures`, surfaced in `LogMealSlot`'s "From plan" unit picker even though the trainer authored the plan in grams) and for custom/off-plan logging (`CustomMealItemPicker`, `IngredientPicker`). Nutrients are always computed from the resulting actual weight, not the reference weight.
- `AddFoodItemDialog`'s Measures editor lets a contributor define an item's own measures (label + grams-per-unit + one default) inline, for both single and composite items; the default measure doubles as the optional entry basis for typing in nutrition values (instead of always per-100g). Reference data is (re)seeded from `backend/ingredient_nutrition_reference.csv` (per-100g values; raw/cooked are separate named rows, e.g. "Chicken breast (raw)" vs. "(cooked)") and `backend/ingredient_measures.csv` (one row per ingredient+measure, `is_default` flag), both read by `seed_food_items`.
- `FoodItem.source` includes `usda` (alongside `seeded`/`off`), with a matching nullable/unique `fdc_id`, for growing the Food Bank from USDA FoodData Central without ever calling it live: `manage.py import_usda_food "<query>"` (`nutrition/usda_client.py` + `management/commands/import_usda_food.py`) searches FDC, shows candidates, and on confirmation `update_or_create`s a `FoodItem` by `fdc_id` (so re-running it updates rather than duplicates) — `source=usda`, `visibility=public`, `approval_status=approved`, same trust level as CSV-seeded rows. `--fdc-id` skips search for a known id, `--auto`/`--yes` skip the interactive prompts for scripted use. Calorie values are special-cased (`CALORIE_NUTRIENT_NUMBERS` in `usda_client.py`): SR Legacy/Branded/Survey foods report plain "Energy" (FDC nutrient #208, kcal), but Foundation Foods omit that in favor of Atwater-factor variants (#957/#958) — the parser tries #208 first, then falls back. `USDA_API_KEY` lives in a gitignored root `.env` (loaded by a few lines in `settings.py`, no dotenv dependency), never called from any user-triggered code path — see `USDA_API_SETUP_SPEC.md` (also gitignored, since it held the raw key).
- **The Food Bank can also be bulk-loaded from USDA's full CSV dump** (`manage.py import_usda_bulk_csv`, Postgres-only — see Deployment step 6a), a deliberate, explicit exception to this app's usual ~10-user scale assumption: once run, the Food Bank holds USDA's *entire* catalog (whole foods + ~2M branded/UPC products), not just curated/on-demand items. This has two real consequences elsewhere: `FoodItem` gained `brand_name` (disambiguates identically-named branded products, e.g. "Chicken Noodle Soup" from a dozen brands — shown alongside the name in `FoodItemCard`/`IngredientPicker` and included in `FoodItemViewSet.search_fields`), and `FoodItemViewSet` is the **one** list endpoint in the app that paginates (`FoodItemPagination`, 25/page) plus gets a Postgres trigram (`pg_trgm`) GIN index on `name`/`brand_name` (migration `0017`, a no-op on SQLite dev) so substring search stays fast at that scale — the index is also declared on `FoodItem.Meta.indexes` (needs `django.contrib.postgres` in `INSTALLED_APPS`), not just in the migration: a vendor-only-skip on the migration's *database* effect (`AddIndexIfPostgres` overrides `database_forwards`/`backwards`, not `state_forwards`) keeps migration *state* identical on every backend, matching `Meta.indexes` everywhere — an earlier version instead made the whole operations list conditional on `connection.vendor` at import time, which left Postgres's reconstructed model state including the indexes while `Meta.indexes` had none, and `makemigrations --check` proposed removing them the first time it ran against Postgres specifically (never caught locally, since dev is SQLite) — every other list endpoint in the app is still small enough to fetch in full by design, don't add pagination there too. `frontend/src/api/foodItems.ts::listFoodItems` returns a `Page<FoodItem>`, not a flat array; `FoodBankPage.tsx` has a "Load more" button, while `IngredientPicker.tsx`/`LogMealPage.tsx` (typeahead, top-N is fine) just read `.results` at a capped page size. `LogMealPage.tsx`'s Bank tab no longer eagerly lists on an empty search (would be a meaningless alphabetical wall of branded products at 2M rows) — it requires typing first, matching `IngredientPicker`'s existing pattern.
- **Barcode scanning** (currently disabled — see Deferred): a floating scan icon on `LogMealPage` (bottom-right, same fixed/rounded-full convention as `FoodBankPage`'s Add button) opens `BarcodeScannerDialog.tsx` — a full-screen camera overlay (portaled to `document.body`, same pattern as `ZoomableChart`'s zoomed view, not a centered `Dialog` — a live camera feed doesn't fit a modal card). Uses `@zxing/browser`/`@zxing/library` rather than the native `BarcodeDetector` API, since Safari/iOS (this app's primary target) doesn't support it at all. Restricted to product-barcode formats (UPC-A/UPC-E/EAN-13/EAN-8). A decoded code is looked up via `FoodItemViewSet`'s `?barcode=` query param (exact match against the unique index, so it stays fast regardless of catalog size) and, if found, added to the log exactly like an existing Food Bank pick; if not, the scanner hands off to `AddFoodItemDialog` pre-filled with the scanned code (`initialBarcode` prop) so the next scan of that product succeeds. **Barcode format normalization** (`nutrition.services.normalize_barcode` / `frontend/src/lib/barcode.ts::normalizeBarcode`, kept in lock-step on both sides): USDA's own `gtin_upc` data isn't width-consistent (12-digit UPC-A, 13-digit EAN-13, 14-digit GTIN-14 all appear for the *same kind* of barcode, and a camera scan of a UPC-A symbol always returns 12 digits) — every barcode is normalized to GS1's own canonical GTIN-14 form (numeric-only, left-padded to 14 digits) both at bulk-import time (`import_usda_bulk_csv.py`) and at scan-lookup time, so a scan matches regardless of which width USDA happened to store; anything non-numeric or longer than 14 digits is treated as not a real barcode.
- **Custom meals** (a floating `Add custom meal` button on `LogMealPage`, same slot/convention as the barcode-scan icon above): a one-time, typed-in estimate for something with no sensible backing item — e.g. "Stew" at a party, where the same dish could get a totally different estimate next time — as opposed to `QuickLogItem` ("My meals"), which is a *reusable* shortcut for something logged identically over and over (e.g. a daily protein shake). `AddCustomMealDialog.tsx` collects a name and calories/protein/carbs/fat (all four required — only the five micros stay optional), then appends straight to the cart — nothing is persisted until the whole meal is saved, and nothing is ever saved for reuse. Backed by `FoodLog.custom_name` (set with `reference_meal_item`/`food_item`/`quick_log_item` all null, source=`custom`) rather than a new model, since a `FoodLog` row already snapshots arbitrary nutrient values — `_compute_nutrients()` just passes the trainee's own typed-in values through unchanged for this source instead of deriving them from a linked item. `LoggedMealItemSerializer` makes calories/macros/micros writable (write-only; `actual_nutrients` still carries them back out on read, same as every other item kind) specifically for this case; both it and the standalone `FoodLogSerializer`, plus `FoodLog.clean()`, all enforce the same "macros required, micros optional" rule for `source=custom` server-side, not just in the dialog's own validation.
  - **Ingredients calculator** (optional, inside the same dialog, collapsed by default — "Enter ingredients (optional)"): reuses `IngredientPicker` (the same Food Bank ingredient search + per-row unit/quantity picker the composite-`FoodItem` builder in `AddFoodItemDialog` uses) to let the trainee add known components instead of guessing a total (e.g. 100g ground beef, 50g tomato). It's a calculator, not a second source of truth: every time the ingredient list changes, its computed total (`nutrientsForWeight` + `sumNutrients`, same client-side math the cart's own totals use) overwrites the calorie/macro/micro fields above, which stay directly editable afterward for a manual nudge (e.g. +50 kcal for a sauce that isn't itemized) — editing the ingredient list again recomputes and overwrites again. Nothing about the ingredient breakdown itself is ever sent to the backend; only the resulting flat numbers are (same as if they'd been typed by hand).
  - **"Head to my meals" link** (below the Add/Cancel row, since a custom meal only affects today's log): closes `AddCustomMealDialog` and opens `AddQuickLogItemDialog` pre-filled with whatever was already typed (name/calories/macros/micros — not the ingredient breakdown, which flattens into those same numbers same as above) via a new `initialValues` prop (replacing the old, narrower `initialName`) — so choosing to save it as a reusable shortcut instead doesn't mean re-typing everything. `QuickLogItem` gained the same 5 micro fields `FoodItem`/`FoodLog` already had (`potassium_mg`/`calcium_mg`/`iron_mg`/`vitamin_c_mg`/`vitamin_a_mcg`, all optional) specifically so this transfer is lossless.
  - Both `AddCustomMealDialog` and `AddQuickLogItemDialog` put `max-h-[85svh] overflow-y-auto` on `DialogContent` itself (mirroring `AddFoodItemDialog`), not on an inner `flex flex-col` form — putting a height cap + `overflow-y-auto` on the *same* element as `flex flex-col` lets the flex-shrink algorithm silently squash a child (their default `flex-shrink: 1`) to fit the cap instead of actually scrolling, which is exactly what happened to the ingredients toggle here during development (visibly rendered at a 2px-tall collapsed height, clipped to nothing) before the fix.
- Every browsable row while logging a meal (plan/"My meals"/Food Bank, in both the combined cross-search view and each per-tab browse view) opens `NutritionFactsDialog.tsx` (that item's calories/macros/micros) when tapped anywhere on the row — not just its ⓘ info icon (same icon convention as the exercise-detail/RPE info icons in Workout, but here the whole row is also a tap target, guarded so a click landing on the Add/Added button doesn't also trigger it — see `BrowseListItem`'s `handleRowClick` in `LogMealPage.tsx`, same "let a nested button opt out" pattern as `ZoomableChart`'s figure-click handler). Deliberately not `FoodItemNutritionFacts`/`FoodItemDetailDialog` (the Food Bank's own detail popup, which is tied to `FoodItem`'s per-100g fields, macro-filter/dietary-tag badges, and alternatives): a plan item's `reference_nutrients` and a `QuickLogItem`'s fixed values aren't `FoodItem`s at all, so `NutritionFactsDialog` instead takes a plain `Nutrients` object (already the common shape `cartItemNutrients` computes for every cart-row kind) plus a caption describing what it's per ("Per serving (Xg)" / "Fixed serving" / "Per 100g") — one component, three data sources, micros that are `null` simply omitted rather than shown as zero. The Food Bank page itself already had this (tap a card to expand → `FoodItemNutritionFacts`, plus "See alternatives" for the fuller `FoodItemDetailDialog`) — the gap this closes was specifically the logging screen.
- Food Bank search with no results shows an inline `Add "<query>" to the Food Bank` link that opens `AddFoodItemDialog` pre-filled with the searched name (mirrored in the Exercise Bank — see section 4 — trainer-only there since only trainers can create exercises).
- Food Bank sharing: private `FoodItem`s are visible only to their creator (no approval needed); public ones need approval from any trainer. Composite items recompute their per-100g nutrition automatically from components. Any trainer can edit/delete any `FoodItem`; a trainee can edit/delete only ones they created themselves. A trainee who can't edit an item directly can instead file a `FoodItemEditRequest` (a freeform description, no structured diff) for a trainer to review and mark resolved — mirrors `ExerciseEditRequest` in the Exercise Bank.
- `macro_filters`/`dietary_tags` back a live "alternatives" query (other items sharing a macro filter, ranked by calorie closeness) — computed at request time, not stored (unlike `Exercise.alternatives`, which is a stored self-M2M since the Exercise Bank is small enough to fetch in full).
- `DietaryTag` doubles as the vocabulary for `User.meal_preferences` (a trainee's own diet-type preference, captured in onboarding's Preferences step and `/profile` via `PreferencesForm`) — unlike `MacroFilter`, it's open-write (any authenticated user, not just a trainer, same trust model as `MuscleGroup`) and carries an optional `description`, since `MultiSelectDropdown`'s generic `onCreateNew` prop lets a trainee type an unlisted diet (e.g. "Carnivore") and add it themselves inline, with a description, rather than being stuck with "No matches." Seeded with a starting vocabulary + descriptions by `seed_food_filters_and_tags`, meant to grow via that flow.
- Nutrient math (`nutrition/services.py::scale_nutrients`/`sum_nutrients`/`average_nutrients`) lives in one place server-side and is mirrored client-side (`lib/nutrients.ts`) for live previews.

### 3. Trainer Connection (Q&A + Notes)
`QAThread` (subject, status open/answered/archived; `trainee_last_read_at` — bookkeeping only, never serialized, backs the unread count below) containing `QAMessage`s — either party can post, change status, or open a new thread (a trainer must name which trainee it's about). `TrainerNote` — trainer-authored, trainee-read-only, auto-marked read as soon as the trainee opens the Notes view; the trainee can additionally archive/unarchive one (`archived` — hides it from their own inbox only, doesn't affect the trainer's sent list or the unread count, since a note is only ever unread before its first view which always precedes archiving), and the trainer can permanently delete one (plain `ModelViewSet` destroy, already permitted server-side by `IsTrainerWriteTraineeReadOnly` — exposed in the trainer dashboard's `TrainerNotesSection` alongside the composer).
- Not to be confused with `TrainerConnection` (section 7) — that's the one-time request to *get* a trainer in the first place; this assumes the relationship already exists.
- `GET /api/connection/unread-summary/` sums the trainee's own unread `TrainerNote`s + unseen `QAMessage`s (everything in a thread after `trainee_last_read_at`, or every non-self message if the thread was never opened) — backs the trainee-side `BottomNav`'s Trainer-tab badge (`lib/useTrainerUnreadCounts.ts`) and `TrainerLayout`'s per-tab Notes/Q&A pill counts, both clearing once the relevant view is opened (`QAThreadViewSet.mark_read`/`TrainerNoteViewSet.mark_read`).

### 4. Exercise Bank
`Exercise` (shared reference data — any trainer can write, all trainees can read, same trust model as `FoodItem`): name, description, equipment, `primary_muscle_groups`/`secondary_muscle_groups` (M2M `MuscleGroup`), difficulty_level, optional image/video_url, self-M2M `alternatives` (non-symmetrical). `PlanExercise` references `Exercise` by FK rather than freeform text. A trainer can add/edit any exercise, with a live front/back muscle-highlight preview (`body-highlighter` package) as primary/secondary muscles are picked; a trainee can't edit directly but can file an `ExerciseEditRequest` (freeform description) for a trainer to review and resolve. Browse UI: search/filter, the same muscle diagram, alternatives resolved client-side from the in-memory ~100-row list. Search with no results shows a trainer-only inline `Add "<query>" to the Exercise Bank` link pre-filled with the query — same pattern as the Food Bank in section 2.

### 5. Daily Tracker
`DailyMetric` (one row per trainee per day: weight+unit, steps, `active_energy_kcal`, sleep hours, bedtime (time-of-day, no date), sleep_quality 1–5, readiness 1–5, water_intake_ml, notes — all optional, upserts on date). `ActivityLog` (activity type + duration, multiple per day, optional calories_burned + notes).
- **Bedtime** (`DailyMetricForm`'s native `<input type="time">`, no seconds) feeds two places: the Daily Tracker form itself, and Progress → Recovery's two new scatter plots (see the Progress Tab section below). It's stored as a plain time-of-day with no date attached; the "8pm-based, wraps past midnight" scale used to chart it alongside the 1-5 ratings is entirely a client-side display concern (`lib/bedtime.ts::bedtimeToScale`/`scaleToClockLabel`/`formatBedtime`) — the raw value is what's sent over the API, same "client-side-only" spirit as PR detection/weight suggestions/the rest timer.
- `GET /api/tracker/daily-summary/?date=` computes a read-side rollup (consumed calories/macros from that day's `FoodLog`s; burned via `tracker/services.py::calculate_tdee` — see below), computed on request and never stored.
- **"Calories out" is `TDEE = BMR + movement energy + TEF`**, where movement energy comes from exactly one of three tiers per day (`tdee-calculation-spec.md` at the repo root, including its two revision notes, for the full history/rationale) — which tier applies is decided independently per day by whatever data actually exists that day, not a global setting, and is reported as `tier: 1 | 2 | 3` on `calories_burned_breakdown`:
  - **Tier 1** — a daily Active Energy total was entered (`DailyMetric.active_energy_kcal`, from the trainee's own device, e.g. an Apple Watch's "Active Calories"): use it directly. Any per-session `WorkoutSession.calories_burned`/`ActivityLog.calories_burned` that day is informational only (exercise history/per-activity detail), not summed in — a wearable's own daily total already reconciles a logged workout/activity's minutes against that same day's step count, so adding them on top would double-count.
  - **Tier 2** — no daily total, but at least one logged workout/activity that day has its own device-reported `calories_burned`: sum those directly (solid data) as `logged_activity_calories`, then subtract the steps those step-generating activities would have contributed (`ActivityMET.steps_per_minute × duration_minutes`, for every step-generating `ActivityLog` that day regardless of whether *that* entry has its own `calories_burned` — the step overlap happened either way) from the day's step count, and convert whatever steps remain to NEAT (`remaining_steps × weight_kg × 0.00057`). `ActivityMET.steps_per_minute` (null = doesn't generate steps) is an approximate walking/running-gait cadence per activity type — only set for an actual footfall gait (walking, running, hiking, court sports, ...); machine-based (cycling, rowing machine, elliptical), water/wheeled/gliding (swimming, skiing, skating), seated (horseback riding), and static (yoga, weightlifting) activities stay null. `WorkoutSession` has no "type" of its own and is always treated as non-step-generating (it's this app's strength-training log).
  - **Tier 3** — no daily total and no per-session calories logged at all that day: NEAT from the *full* day's steps, nothing subtracted. Never estimated from duration/MET tables — too imprecise to present with Tier 1/2's confidence — so a logged workout/activity with no calories entered still stores its own duration/sets for history, just contributes `0` to the total. Flagged as a lower-confidence, partial-data estimate in the UI (a "≈" prefix on `DailySummaryCard`'s "Calories out" number, and an "estimate" label + amber-tinted row in `CaloriesOutInfoDialog`).
  - **BMR**: Mifflin-St Jeor from `User.height_cm`/`age`/`sex` and weight *as of that date* (`accounts/services.py::resolve_weight_kg_as_of`, distinct from `resolve_current_weight_kg` — BMI/Goals want today's true latest regardless of what date is being viewed elsewhere, but a past day's TDEE shouldn't use a weight logged after it; `compute_bmr(user, as_of=date)` takes the same optional param). `DailyMetric.steps` stays purely a movement metric shown for its own sake (Daily Tracker form, Progress charts) outside of feeding NEAT in Tiers 2/3 above — never converted to calories in Tier 1.
  - **TEF**: `10%` of that day's logged food calories (`FoodLog`), `0` if nothing's logged yet — additive in all three tiers.
  - `ActivityLog.activity_met` (FK to `ActivityMET`: `name`, `met_value`, `steps_per_minute`) is a self-seeded table (`manage.py seed_activity_mets`, ~50 rows from the Compendium of Physical Activities, no live third-party dependency), open-write (any authenticated user, same trust model as `nutrition.DietaryTag`) since a trainee logging an activity that isn't listed yet needs to add it themselves. The frontend's `ActivityLogSection` picks it via `SearchableSelect` (`components/SearchableSelect.tsx` — single-choice sibling of the checkbox-based `MultiSelectDropdown`, same visual language and `onCreateNew` affordance); typing something new opens a small dialog (mirrors `PreferencesForm`'s dietary-tag `onCreateNew` flow) with the name pre-filled, an editable MET value defaulted to `4.0` (moderate), and a "Generates steps" `Switch` (off by default) that reveals a steps-per-minute input (defaulted to `110`) when on. Corrections afterward go through Django admin, not in-app UI — small, rarely-touched table, not a Bank needing full CRUD.
  - Any missing input degrades gracefully (`bmr` comes back `null`, the total still includes whatever else is known) rather than refusing to answer. The frontend's `DailySummaryCard` "Calories out" tile has an ⓘ icon (`CaloriesOutInfoDialog`) breaking the estimate into BMR, whichever tier's line(s), and TEF, mirroring the RPE info-icon pattern in section 1. When `bmr` comes back `null` (height, age, or a resolvable weight missing — `sex` alone never triggers this, since `Sex.UNSPECIFIED` just averages the male/female term), the tile gets a subtle `ring-destructive/40` outline and the dialog's "Add your height, age, and weight in Profile" line renders "Profile" as a link to `/profile` that auto-scrolls to `BodyForm` (`id="body-form"`, via `ProfilePage`'s `location.state.scrollTo`). Tiers 2/3 get a same-page deep link inviting a daily Active Energy total instead (`document.getElementById('daily-active-energy-field')` + `scrollIntoView`, no router state needed since `CaloriesOutInfoDialog` only ever renders on the Daily tab) — but deliberately without the tile's red ring, since (unlike the one-time BMR/profile gap) going without a watch total some/every day is an expected, recurring, non-error state.
  - **Under-target flagging** (`lib/dietStatus.ts`, used by `DailySummaryCard` and the Diet tab's own day cards): calories reads as bad outside a 90–110% band of the target (too low *or* too high), but protein only ever needs a *minimum* — bad below 90% of target, fine at or above it, since overshooting protein isn't a problem worth flagging. `DailySummaryView` resolves that protein target as `planned.protein_g` (the trainer's diet plan) when set, else falls back server-side to a 1g-per-lb-bodyweight estimate (`tracker/services.py::estimate_minimum_protein_g`, same per-date weight resolution TDEE/BMR use) — surfaced as `protein_minimum_g` + `protein_minimum_is_estimate` on the response, with the frontend prefixing an estimated target with "≈" (e.g. "P 0g / ≈176g") so it doesn't read as an actual trainer-set number. This fallback is wired into the Daily tab's own summary only for now — the Diet tab's day-by-day Progress/Log browsers (`ProgressDayCard`/`LogDayCard`/`ProgressSummaryCard`) still only flag protein when the trainer's plan sets an explicit target.

### 6. Settings & Personalization
Hamburger menu (`NavDrawer`): Profile, Goals, Plan Management (pure nav shortcut), Units & Preferences, Reminders, Data Export.
- `Goal` (weight or strength type, optional target_date, `is_active`) is jointly owned: a trainee can always add/edit/remove their own goals, and once a trainer is assigned that trainer can too (`GoalWritePermission`) — either side's changes are visible to both, with no read-only lockout in either direction. A weight goal is still stored as `target_weight`/`target_weight_unit`/`direction` (all three), but the frontend (`GoalForm`, `GoalsOnboardingCard`) never makes the trainee set `direction` manually when a current weight is resolvable: a "Target weight" / "Lose or gain amount" toggle either derives direction by comparing the typed target against `current_weight_kg` (`lib/weightGoal.ts::directionFromTarget`), or derives the target weight from a typed amount (`targetWeightFromAmount`). Manual direction picking is only a fallback shown when `current_weight_kg` is null (no starting weight or `DailyMetric` logged yet). `current_weight_kg` itself (`accounts.services.resolve_current_weight_kg`) is exposed both on `Goal` (existing goals) and on `User`/`UserSerializer` (so a brand-new goal's form has it before any goal exists).
- `UserPreference`/`ReminderSetting` are fully private to the owner (no trainer branch at all) — personal account settings, not training data.
- `Notification`/`PushSubscription` back reminder delivery (real Web Push via `pywebpush`, dev-only VAPID keys in `config/settings.py`). Delivery runs via the `send_due_reminders` management command, intended for a plain OS cron entry — **no Celery/task queue yet** (see Deferred).
- Data Export: 3 self-only CSV endpoints (diet/workout/daily-metrics), date-range filtered.

### 7. Onboarding Wizard & Initial Trainer Assignment
Self-service **signup** (`POST /api/auth/signup/`, trainee-only — trainers stay admin-provisioned). A 4-step `/onboarding` wizard (Baseline → Goals → Preferences → Trainer Connection), skippable/resumable, sharing components with `/profile`.
- Baseline fields (`height_cm`, `age`, `sex`, `starting_weight`) live directly on `User` — `sex` (male/female/unspecified, default unspecified) exists only to feed the Daily Tracker's BMR estimate (see section 5), captured alongside the others in `BodyForm`/onboarding's Baseline step, not used anywhere else. A computed (never stored) `bmi`/`bmi_category` is resolved via `accounts/services.py`, using the latest `DailyMetric` weight if one exists, else `starting_weight`.
- `TrainerConnection` (`connection` app): `option_selected` (no_preference/specific_trainer/train_myself — the last rejected server-side, shown "coming soon" in the UI), `status` (pending_manual_assignment/active/not_applicable), `assigned_trainer`. Assignment is a **manual Django admin action** — setting `assigned_trainer` also flips `status` to `active` and syncs `User.trainer` in one `save()` override.

### 8. Trainer Dashboard
The trainer's actual workspace.
- **Trainee roster** (`/trainees`): every trainee via `User.trainer`, searchable by name, filterable by weight trend / consistency % / days-inactive — all computed in Python (`trainerdashboard/services.py`), not an ORM aggregation (fine at this app's scale).
- **Trainee detail** (`/trainees/:id`): a Goals section plus tabs for Diet Plan, Workout Plan, Progress (read-only, scoped), Notes & Q&A.
- **Diet/Workout plan editing is real, full CRUD** (create/edit/delete/reorder at every level) — the backend already permitted this via existing `IsTrainerWriteTraineeReadOnly` viewsets; this was purely a frontend gap. Every edit is logged to `PlanChangeLog` (a one-line summary, not a diff) via a shared `PlanChangeLoggingMixin`.
- **Live diet-plan nutrition while editing** (`plan-editor/PlanNutritionSummary.tsx`, client-side only): a "Daily total" card above the meals sums one option per meal — each meal's first option by default, with a per-meal option dropdown once any meal has alternatives — and each meal/option header shows its own kcal/P/C/F. Totals follow the trainer's *unsaved* ingredient drafts as they type (`MealOptionEditor` reports `draftNutrients` up to `DietPlanEditor`; saved-but-unchanged rows rescale their `reference_nutrients`, newly added rows scale from the `FoodItem`'s per-100g), falling back to the option's saved `nutrients` once its editor unmounts.
- `TrainerPrivateNote` (trainer-only scratchpad, never trainee-visible) is distinct from the trainee-visible `TrainerNote` in section 3 — both are trainer-deletable (plain `ModelViewSet` destroy).

### Progress Tab
A read-only cross-category dashboard: an Overview chart plus Training/Nutrition/Recovery/Consistency sub-dashboards, one shared date-range control (today/yesterday/week/month/~10yr "all time"/custom). Backed by six pure-aggregation `/api/progress/` endpoints (`progress` app, no new models). PR events and every chart are computed/rendered client-side as hand-rolled inline SVG (no charting library, kept consistent with the rest of the app); Session History and Diet History browsers expose exact past logs. The Photos section is a placeholder (`ProgressPhoto` deferred).
- **Zoomable charts**: every hand-rolled SVG chart (Overview, Nutrition's macro trend, Diet -> Progress's nutrient trend, Exercise history, Training volume/frequency's two bar charts, Recovery) is wrapped in `components/charts/ZoomableChart.tsx` — wrapped around the chart component's own top-level return (not at its call site), so internal state (series toggles, selected day, ...) stays owned by one component instance regardless of where its output is portaled to. It renders a zoom icon immediately in front of the chart's own title; charts whose title used to live in a sibling `CardHeader`/`CardTitle` (Overview, Recovery, Nutrition's "Calories & macros vs. target") had that removed since the chart now renders its own — `ChartEmptyState` (same file) keeps the title visible through the loading/no-data branches too. Zooming in is icon-only (tapping the figure itself used to zoom too, but that made interacting with a chart's own legend/series-toggle buttons and data points feel accident-prone). Zoomed is a full-screen portal to `document.body`; on a phone held in portrait it's rotated 90° into a simulated landscape view (`.chart-zoom-overlay` in `index.css`) so a wide chart gets the phone's long axis without physically rotating the device — the close (X) button lives outside that rotated box, pinned via `position: fixed` to the real screen corner, so it stays upright and reachable regardless of the rotation.
- **Overview chart's weight axis is deliberately not zero-floored**, unlike its other four series (`OverviewChart.tsx::computeWeightAxis`, vs. the shared `computeAxis` everything else still uses): a realistic weight change (e.g. 155→150lb) would be an invisible sliver on a 0-anchored axis. Instead the axis hugs the data — 10lb past whichever end is "further along" toward an active weight goal (below it for a loss goal, above it for a gain goal, detected by whether the goal sits below or above the actual data's own peak — no explicit `direction` lookup needed) and 10lb past the actual recorded extreme on the other end; with no goal, both ends are just 10lb past their respective actual extreme. Converts the 10lb padding through `lib/weightUnits.ts` so it's a real 10lb regardless of the viewer's kg/lb display preference.
- **Overview chart's weight is actually two lines**: a thin, low-opacity overlay of the raw daily readings, plus a bold 7-day trailing moving average (`movingAverage`, the mean of whatever non-null readings fall in the 7 calendar days ending on each point, not just the last 7 log entries) - the bold line is what actually reads as the trend under realistic day-to-day noise (water, food volume, ...). The raw overlay has its own "Daily weight" toggle, a sub-option of the main "Weight" legend pill (only shown/togglable while weight itself is on) rather than a full second entry in `SeriesKey`, since it shares the same axis and doesn't need one.
- Training's per-exercise Strength view (`TrainingStrengthPanel`) additionally shows an all-time PR summary (independent of the selected date range) and a toggleable Volume (Σ weight×reps per day) line alongside weight/avg-reps-per-set on `ExerciseHistoryChart`; clicking any date column on that chart shows an inline box with that day's exact weight/reps/volume. Fetching a trainee's exercise history from here requires passing `trainee_id` explicitly (see `listExerciseHistory`) — the trainer-dashboard-by-id exception above doesn't cover this endpoint since it's a `list` action, not retrieve/update/destroy.
- **Recovery** has three cards: the existing sleep-quality/readiness trend (`RecoveryChart`), plus two scatter plots below it (`BedtimeScatterChart`, parameterized by which rating to plot) — bedtime vs. sleep quality, and bedtime vs. readiness, one point per day. The x-axis is `lib/bedtime.ts`'s 8pm-based scale (floored at 8pm, hugging the latest bedtime in range but never less than 6am's worth of span so the plot isn't cramped when bedtimes cluster), formatted back to clock-time tick labels (`scaleToClockLabel`); the y-axis reuses the trend chart's own 1-5 `RATING_LABELS`. Tapping a point shows a small tooltip (date, exact bedtime, rating) via the same `selectedDate`-keyed pattern `RecoveryChart`'s own trend line already uses. A day only becomes a point on a given plot once it has *both* a bedtime and that specific rating logged - `ProgressRecoveryView` now includes a day if any of the three (sleep_quality/readiness/bedtime) is set, not just the two ratings.

## Conventions

- RESTful, resource-oriented endpoints (`/api/workouts/sessions/`, `/api/nutrition/food-items/`, ...).
- Nutrient math belongs in a model method or `services.py`, never duplicated in views/serializers.
- Write a migration for every model change; never hand-edit migration files.
- DRF serializers + viewsets over hand-rolled views unless there's a good reason not to.
- Small, feature-scoped frontend components (`WorkoutLogger`, `FoodLogEntry`, etc.) over large page components.
- Structured logs that replace-on-relog (`LoggedMeal`, `WorkoutSession`, `DailyMetric`) always POST/PUT the **complete current state**; the backend upserts. Don't build granular per-field PATCH flows for these.
- Client-side-only concerns, deliberately not backend fields: PR detection, weight suggestions, rest timer, moving averages — anything derivable from already-fetched history, kept off the API so tweaking the logic never needs a version bump.
- A dropdown/search list living inside a card must be a portaled Radix `DropdownMenu`/`Popover`, never an absolutely-positioned `<div>` — cards use `overflow-hidden` and will clip it.
- Avoid horizontally-scrolling pill/filter rows at mobile width — use a `Select` dropdown or an icon+label row instead.
- Destructive actions (delete a goal/session/exercise/...) confirm via the app-styled `components/ConfirmDialog.tsx` (`variant="destructive"`, the default), never the browser's native `window.confirm`. The same component also backs a non-destructive staged-then-confirmed change (`variant="default"`, plus an optional `confirmingLabel` override for the in-flight button text, which otherwise defaults to "Deleting…") — e.g. `QAThreadDetail`'s status `Select` stages a `pendingStatus` locally and only PATCHes on explicit confirm via a "Save status" button, rather than saving immediately on selection.
- Any hand-rolled SVG chart gets zoom-to-fullscreen for free via `components/charts/ZoomableChart.tsx` — wrap the chart component's own top-level return (not its call site) so its internal state survives zooming; see the Progress Tab section for the full pattern (title/icon placement, `ChartEmptyState`, the forced-landscape CSS).
- A boolean that reads as an on/off *state* (e.g. Reminders' Enabled/Disabled) uses `components/ui/switch.tsx` (Radix `Switch`) so it visually reads as a toggle at a glance; reserve the pill-style `Toggle` component for filter-chip-like choices instead.
- The app is installed as an iOS home-screen PWA (`apple-mobile-web-app-status-bar-style: black-translucent`, `viewport-fit=cover`), so content renders under the status bar/Dynamic Island. Any element that must occupy exactly its own rendered box there (the sticky `Header`, or a sticky sub-nav pinned `top: calc(var(--header-height) + env(safe-area-inset-top))` under it) must fold the safe-area inset into `height`/`top` via `calc()` — never apply it as extra `padding` alongside a separately-fixed height, since the global `box-sizing: border-box` then shrinks the content box instead of growing the element. The bug is easy to miss on a small-inset device (iPhone 12) and only becomes visible on a larger one (Dynamic Island iPhones) — see `layout/Header.tsx`/`layout/BottomNav.tsx` for the correct pattern.
- No auth/infra complexity beyond ~10 users' needs — flag it if a request looks like scope creep for this stage.
